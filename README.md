# Solar Generation API

A REST API for managing Sri Lankan solar installation and generation data. It
provides jurisdiction-scoped read access for SLSEA users and an authenticated
write path for metering devices. The service is built with Node.js, Express,
MongoDB, and Mongoose.

## Features

- Province → district → grid substation → solar installation hierarchy.
- Append-only generation readings, per-installation history, and cross-site
  history queries.
- National, province, and district user roles with server-enforced read scope.
- Separate user and metering-device JWT authentication.
- Device tokens are bound to one installation; devices can only submit readings
  for that installation.
- Pagination, time and jurisdiction filters, timestamp sorting, and ETag-based
  conditional GET requests.
- Consistent JSON error responses and OpenAPI documentation with Swagger UI.
- MongoDB seed data and a district generation summary endpoint.

See [data-model.md](data-model.md) for entities, relationships, indexes, and
jurisdiction rules. [project.md](project.md) contains the coursework blueprint
and [implementation-plan.md](implementation-plan.md) records the planned phases.

## Requirements

- Node.js 20 or later (ES modules are used).
- MongoDB 7 or later, locally or through MongoDB Atlas.
- npm.

## Setup

```bash
npm install
```

Copy `.env.example` to `.env`, then set the values for your environment:

| Variable | Purpose | Default/example |
|---|---|---|
| `PORT` | HTTP port | `3000` |
| `NODE_ENV` | Runtime environment | `development` |
| `MONGODB_URI` | MongoDB connection string | `mongodb://127.0.0.1:27017/solar-generation` |
| `JWT_SECRET` | Signing key for SLSEA user tokens | Replace the example with a long random secret |
| `DEVICE_TOKEN_SECRET` | Signing key for metering device tokens | Replace the example with a different long random secret |
| `API_BASE_URL` | Base URL shown in the OpenAPI document | `http://localhost:3000` |

Keep `.env` and production secrets out of version control. The `.gitignore`
also excludes `device-tokens.json`, which is generated by the seed command.

## Run the service

```bash
npm run dev
```

For a regular start:

```bash
npm start
```

The server connects to MongoDB before listening. By default, it listens on port
3000. Visit `/` for the project landing page, `/health` for the health check,
`/api-docs` for Swagger UI, or `/api-docs.json` for the OpenAPI document.

## Seed the database

```bash
npm run seed
```

The seed script clears the configured database collections and repopulates
them from the JSON fixtures in `src/database/seed/data/`. It creates device
tokens in the ignored `device-tokens.json` file. **Use a disposable development
database:** seeding deletes existing data. In production, the script refuses
to run unless explicitly invoked with `--force`.

The fixture set includes 9 provinces, 25 districts, substations, installations,
readings, and four users for national, province, and district access examples.
Review the fixture data and seed implementation for the current dataset and
test account details. Do not expose generated device tokens or account secrets.

## API overview

The API is rooted at `/api/v1`. Except for login, read endpoints require a user
JWT in `Authorization: Bearer <token>`. Reading ingestion requires a device JWT.
Use the OpenAPI page for complete schemas, parameters, headers, and response
codes.

| Method | Path | Access | Purpose |
|---|---|---|---|
| `POST` | `/auth/login` | Public | Exchange user credentials for a JWT |
| `GET` | `/provinces` | User | List provinces |
| `GET` | `/provinces/:provinceId` | User | Read a province |
| `GET` | `/provinces/:provinceId/districts` | User | List its districts |
| `GET` | `/districts/:districtId` | User | Read a district |
| `GET` | `/districts/:districtId/substations` | User | List its substations |
| `GET` | `/districts/:districtId/generation-summary` | User | Read aggregate generation summary |
| `GET` | `/substations/:substationId` | User | Read a substation |
| `GET` | `/substations/:substationId/installations` | User | List its installations |
| `GET` | `/installations/:installationId` | User | Read installation and hierarchy context |
| `GET` | `/installations/:installationId/last-reading` | User | Read its newest reading |
| `GET` | `/installations/:installationId/readings` | User | List an installation's reading history |
| `GET` | `/installations/:installationId/readings/:readingId` | User | Read one reading |
| `GET` | `/readings` | User | Query readings across installations |
| `POST` | `/installations/:installationId/readings` | Device | Append a reading for its assigned installation |

Collections support `page` and `limit` (default 10, maximum 100). Reading
collections support `from`, `to`, and `sort=timestamp:asc` or
`sort=timestamp:desc`. `/readings` additionally supports `provinceId`,
`districtId`, and `substationId`. Unsupported query parameters are rejected.

Successful reads return an `ETag`. Send the value in `If-None-Match` to receive
`304 Not Modified` when the representation has not changed. Collections use a
`{ "data": [], "pagination": { ... } }` response. Errors follow this shape:

```json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "Installation not found.",
    "detail": "No installation exists for the supplied identifier."
  }
}
```

Readings are append-only; `PUT`, `PATCH`, and `DELETE` are not supported.
Successful ingestion responds with `201 Created` and a `Location` header.

## Example requests

Log in (use an account from the seeded fixture or your own user record):

```bash
curl -X POST http://localhost:3000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"user@example.com","password":"your-password"}'
```

Read provinces with the returned user token:

```bash
curl http://localhost:3000/api/v1/provinces \
  -H 'Authorization: Bearer <user-token>' \
  -H 'Accept: application/json'
```

Submit a reading with the device token generated for that installation:

```bash
curl -X POST http://localhost:3000/api/v1/installations/<installation-id>/readings \
  -H 'Authorization: Bearer <device-token>' \
  -H 'Content-Type: application/json' \
  -d '{"timestamp":"2026-01-15T06:00:00.000Z","powerKw":12.4,"energyKwh":128.6,"voltage":230.1}'
```

The `installationId` is taken from the URL and checked against the device
token. A reading with an existing installation/timestamp pair conflicts.

## Deployment notes

Set the required environment variables in the hosting platform, use a
production MongoDB database, and set `API_BASE_URL` to the public HTTPS URL so
the OpenAPI server link is correct. Seed deliberately and verify `/health` and
`/api-docs` after deployment. Keep signing keys, user credentials, and generated
device tokens private.
